# paredit-feature-rename

Renaming symbols, functions, control targets and their references across a workspace.

## Responsibilities

The largest feature in the workspace, and the one where being wrong is most
expensive: a rename that misses a reference produces code that still parses and
no longer works.

- **`refactor rename`** — renames a binding, function, macro, symbol macro,
  class, slot, package-qualified symbol or method, updating every reference
  that genuinely refers to it.
- **`refactor rename-control`** — renames a control target: a `block` name, a
  `tagbody` tag, a `go` label, a loop's named exit.
- **`rename_types`** — the shared vocabulary both use to describe an
  occurrence, a scope, and a refusal.

The whole difficulty is deciding what "genuinely refers to it" means. A symbol
with the same spelling may be a different binding under shadowing, a keyword, a
quoted datum, a package-qualified symbol from elsewhere, a slot accessor
generated by `defclass`, or a name inside a `macrolet` body that will never
exist at runtime. Each of those is a separate module under `rename/domain`, and
each exists because the naive answer was wrong.

### What this package does not own

- **No package renaming.** Renaming the *package* is `feature/package`;
  renaming something *in* one is here.
- **No scope analysis.** Which binding a name refers to is answered by
  `paredit-core-semantics`; this package decides what to do with the answer and
  where the naive answer needs qualifying.
- **No span surgery or safety refusals.** Those are `paredit-core-edit`.

## Dependencies

| Crate | Why |
| --- | --- |
| `paredit-core-syntax` | Occurrences are atoms in a tree, and the reader's case and package-qualifier rules decide when two spellings are the same symbol. |
| `paredit-core-semantics` | Shadowing, binding provenance and cross-file resolution — the facts every refusal here is built on. |
| `paredit-core-edit` | Span replacement and the shared mutation-safety refusals. |
| `paredit-core-workspace` | Renaming is workspace-wide by default. |
| `paredit-core-cli` | Input reading, atomic writes, shared argument types. |
| `clap`, `serde_json`, `anyhow`, `thiserror` | Arguments, output, fallible paths. |
| `proptest` (dev) | Properties over generated definitions and references: every occurrence renamed or none, and the output must re-parse. |

## Public API

Two `(Args, run)` pairs, per §4.2 — `rename` and `rename_control`.
`rename_types` publishes the occurrence vocabulary that
`feature/inline`'s `inline_literal_constant` also needs, via
`collect_define_symbol_macro_reference_renames`. That is a deliberate
feature-to-feature edge and the reason this package had to be extracted before
that slice could leave the root.

`#[non_exhaustive]` is deliberately absent (§9.4).

## Layout

Slice-first, per §3.1 — three slices, but `rename`'s domain is deep because
each qualification of "same symbol" earns its own module:

```text
src/
├── rename/
│   ├── domain.rs + domain/     one module per kind of thing that can be
│   │                           renamed, plus the shadowing and macrolet rules
│   ├── usecase.rs + usecase/
│   └── cli/
├── rename_control/{domain.rs + domain/, usecase.rs, cli.rs}
└── rename_types/{domain.rs}
```

§3.1's exception applies here: when one slice runs to thousands of lines, it
may subdivide internally. The unit to split by is what a reader would go
looking for — "how does this handle `macrolet`?" — not which layer it belongs
to.

## When you change this package

| You are… | and it belongs here because… |
| --- | --- |
| fixing a reference that should have been renamed and was not | occurrence discovery is here, module by module |
| fixing a reference renamed that should not have been | usually a shadowing or quoting rule in `rename/domain` |
| teaching rename about a new definition form | it gets a module under `rename/domain` |
| changing what a rename refuses to do | the refusals live with the rule that raises them |

| You are… | and it does **not** belong here because… |
| --- | --- |
| renaming a package | that is `feature/package` |
| changing how scope or shadowing is computed at all | that is `core/semantics` |
| changing how the file is written | that is `core/cli` |

Adding a dependency to `Cargo.toml` means adding a row to the table above.
